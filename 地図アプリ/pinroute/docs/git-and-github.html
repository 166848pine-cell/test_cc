1GitとGitHubは別のもの

まずここを分けて考えると、あとが一気に分かりやすくなります。

Git — 手元で動く「記録係」

  • あなたのパソコンにインストールされているソフト
  • フォルダの中身の変化を記録し続ける
  • ネットにつながっていなくても動く
  • GitHubがなくても使える

GitHub — ネット上の「置き場所」

  • Gitの記録を預けて共有できるサービス
  • 他の人に見せる・一緒に作業する
  • 自動でテストしたり、Webサイトとして公開したりもできる
  • 似たサービスにGitLab、Bitbucketなどもある

たとえるなら Git = 手元のノート、GitHub = そのノートを置いておく貸金庫です。 ノートは自分だけで使ってもよく、貸金庫に預ければ他の人と共有できます。 「Gitを使う=GitHubを使う」ではありません。

2そもそも何が嬉しいのか

Excelでよくある「最終版問題」を思い浮かべてください。

Gitがないとき

  • 企画書.xlsx
  • 企画書_修正.xlsx
  • 企画書_修正_最新.xlsx
  • 企画書_最終.xlsx
  • 企画書_最終_本当に最終.xlsx

どれが最新か分からない。誰が何を変えたかも分からない。

Gitがあるとき

  • ファイルは企画書.xlsx だけ
  • 変更の履歴はGitが別に持っている
  • 「いつ・誰が・どこを・なぜ」変えたかが残る
  • 好きな時点の状態に戻せる

フォルダはいつも1つ。履歴は横に積み上がっていく。

3Gitの3つの場所(最重要)

ここが分かればGitの8割は分かったようなものです。

Gitでは、ファイルは3つの場所を順に移動していきます。 いきなり記録されるのではなく、「記録するものを選ぶ」段階が間にあるのが特徴です。

図1 — ファイルが記録されるまでの3段階

① 作業フォルダ いま編集している
実際のファイル
→git add
② ステージ 次の記録に
含めるものの置き場
→git commit
③ 履歴 確定した記録
(消えない)

なぜ「ステージ」があるのか

10個のファイルを直したけれど、そのうち3個だけを1つの記録にまとめたい、 ということがよくあります。ステージは「今回の記録に入れるものを選ぶカゴ」です。

図2 — 直したもの全部ではなく、選んで記録する

作業フォルダ ・style.css を修正
・main.ts を修正
・メモ.txt を修正
→git add style.css main.ts
ステージ ・style.css
・main.ts
(メモ.txt は入れない)
→git commit
1つの記録 「見た目を調整」
として履歴に残る

よくある勘違い git add は「ファイルを追加する」ではなく 「次の記録に含める、と決める」という意味です。 すでにあるファイルを修正したときにも毎回 git add が要ります。

4コミット = 記録の1コマ

コミットは「セーブポイント」。それが1本につながって履歴になります。

コミット(commit)とは、その時点のフォルダの状態を丸ごと記録したものです。 1つ1つに固有の番号と説明文(メッセージ)が付きます。

図3 — コミットは古いものから順につながっていく

29d4e56 test.md を追加
6d315cd brunch.md を置いた
8fb97f3 brunch.md に中身を書いた いまここ

※ これは実際にお手元のリポジトリにある3つのコミットです

29d4e56 のような文字列はコミットの名前です(本当は40文字ありますが、 先頭7文字だけで区別できるので短く書きます)。 「あの時点に戻したい」というとき、この名前で指定します。

メッセージが大事 コミットのメッセージは未来の自分への手紙です。 「修正」ではなく「検索結果が関連度順に並ぶよう修正」のように書いておくと、 半年後に履歴を見たときに助かります。

5ブランチ = 履歴の枝分かれ

本編を壊さずに、別の作業を並行して進めるための仕組みです。

ブランチ(branch = 枝)は、履歴を枝分かれさせる機能です。 「今動いているもの」を残したまま、別の場所で新機能を試せます。

図4 — main から枝を伸ばして作業する

A最初
B機能1 main
C試作
D仕上げ test_cc

枝の上でどれだけ作業しても、main の側はB のまま変わりません。 失敗したら枝ごと捨てればよく、うまくいったら次章の「マージ」で本編に取り込みます。

ブランチ名の慣習 main は「本編・完成版」を置く枝として使われるのが一般的です (以前は master と呼ばれていました)。 作業用の枝には内容が分かる名前を付けます。

6マージと「競合」

枝を本編に合流させる作業と、そこで起きるトラブルの話です。

マージ(merge)は、枝で行った変更を別の枝に取り込むことです。

図5 — たいていは自動で合流できる

main Aファイルを変更
＋
test_cc Bファイルを変更
→git merge
合流できた 別の場所を触っているので
Gitが自動で判断できる

競合(コンフリクト)が起きるとき

両方が同じファイルの同じ行を変更していたとき、 Gitはどちらを採用すべきか判断できません。これが競合です。

図6 — 同じ行を別々に直すと、人が決めるしかない

こちらでは 1行目を
「testだよ」に
＋
あちらでは 1行目を
「ブランチtest」に
→
競合 Gitは決められない
人が選ぶ

競合が起きると、Gitはそのファイルに両方の案を並べて書き込みます。 実際にこのリポジトリの brunch.md は、しばらくこの状態のままでした。 

<<<<<<< Updated upstream   ← ここから下が「取り込む前からあった方」
testだよ
=======                       ← 区切り線
ブランチtest
>>>>>>> Stashed changes    ← ここまでが「あとから来た方」

直し方は2通りあります。

  1. どちらかを残す場合:ファイルをテキストエディタで開き、残したい文だけにして <<<<<<< ======= >>>>>>> の3行を消す。保存して git add <ファイル>(=「解決しました」の合図)
  2. そのファイル自体が不要な場合:git rm <ファイル> で削除する。 これも「解決した」とみなされる

このリポジトリでは brunch.md はもう使わないファイルだったため、2番目の方法 (git rm brunch.md)で削除して解決しました。 削除しても過去のコミットからは消えません。 6d315cd と 8fb97f3 の時点の内容はいつでも取り出せます。

競合が残っているとどうなるか そのリポジトリでは新しいコミットができません。 「途中で止まっている」状態なので、Gitが先へ進ませてくれないのです。 エラーが出て困ったときは、まず git status で Unmerged paths と書かれていないか確認してください。

7手元とGitHubのやりとり

送る(push)・取ってくる(pull)・複製する(clone)の3つだけです。

図7 — 同じ履歴が2か所にある

あなたのパソコン ローカルリポジトリ
(作業フォルダ + 履歴)
→git push(送る)
←git pull(取ってくる)
GitHub リモートリポジトリ
通称 origin
したいこと コマンド 意味
GitHubにあるものを手元に持ってくる(最初の1回) git clone <URL> 丸ごと複製する
手元の記録をGitHubに送る git push 押し上げる
GitHub側の新しい記録を手元に取り込む git pull 引っ張ってくる

origin とは 「送り先のGitHubリポジトリ」に付けられたあだ名です。 毎回 https://github.com/… と打つのは大変なので、 origin という短い名前で呼べるようにしてあります。 git push origin main は 「originという場所へ、mainという枝を送る」という意味です。

大事な性質 コミットしただけではGitHubには反映されません。 コミットは手元のノートに書くこと、pushは貸金庫に預けること。 この2つは別の操作です。

8GitHubがしてくれること

保管だけではありません。今回の公開もこの機能を使っています。

機能 できること
リポジトリ 履歴を預かる。誰がいつ何を変えたかをWeb画面で見られる
Issues 「ここを直したい」を課題として登録・管理する
Pull Request 枝の変更を本編に入れる前に、内容を見せて相談する
Actions pushをきっかけに、テストやビルドを自動で実行する
Pages 指定フォルダをWebサイトとして無料で公開する

PinRoute の公開では、この最後の2つを使っています。 git push するとActionsが自動でテストとビルドを行い、 できあがったファイルをPagesが配ります。

公開のときの注意 無料プランでPagesを使う場合、リポジトリを公開(public)にする必要があります。 公開するとそのリポジトリの中身と過去の履歴がすべて誰でも見られる状態になります。 一度コミットしたものは履歴に残るため、パスワードや個人情報を含むファイルを 過去にコミットしていないか確認してから公開してください。

9いまのあなたのリポジトリ

ここまでの用語で、現状を読んでみます。

図8 — 2026年7月時点の test_cc リポジトリ

29d4e56 test.md を追加
6d315cd brunch.md を置いた main
8fb97f3 brunch.md に中身 test_cc ← いまここ

GitHub側(origin)も同じ位置にあります。ここまでは手元とGitHubが一致しています。

まだ記録されていないもの

brunch.md 削除した
ステージ済み
test.md 手元から消えているが
まだステージしていない

brunch.md だけ色が違うのは、すでにステージに入っているからです (第3章の②の位置)。ほかの3つはまだ作業フォルダにあるだけで、 次のコミットには含まれません。

つまり PinRoute はまだGitの履歴に一度も入っていません。 あなたのパソコンの中にあるだけの状態です。 公開するには、この順に進める必要があります。

↓
② 記録するものを選ぶ(git add) 地図アプリ/ と .github/ をステージに入れる
↓
③ 記録する(git commit) 説明文を付けて履歴に確定させる
↓
④ main に取り込む(git merge) 公開の設定が main を見ているため

↓
⑥ GitHubの画面で公開設定をする リポジトリを公開にし、Pages のSourceを「GitHub Actions」に

10コマンド早見表と用語

迷ったら git status。いまの状況と次にすべきことを教えてくれます。

コマンド 意味
git status いまの状態を見る。何が変更され、何がステージにあるか
git add <ファイル> 次の記録に含める
git add . 変更したものを全部含める
git commit -m "説明" ステージの内容を履歴に記録する
git log --oneline 履歴を一覧で見る
git switch <枝名> 別のブランチに移動する
git switch -c <枝名> 新しいブランチを作って移動する
git merge <枝名> その枝の変更を、いまいる枝に取り込む
git push origin main mainブランチをGitHubへ送る
git pull GitHub側の新しい記録を取り込む
git diff 何をどう変えたかを行単位で見る

用語辞典

リポジトリ
履歴を含めたプロジェクト一式。「repo(レポ)」とも呼ぶ
コミット
その時点の状態の記録。1つずつ名前(ハッシュ)と説明文を持つ
ステージ
次のコミットに含めるものを置く場所。index とも呼ぶ
ブランチ
履歴の枝。本編を壊さずに別作業を進めるためのもの
main
本編にあたるブランチの一般的な名前
HEAD
いま自分がいる位置。「いまここ」を指す印
マージ
枝の変更を別の枝に取り込むこと
コンフリクト
同じ行を別々に変更していて、Gitが判断できない状態
origin
送り先のGitHubリポジトリに付けられたあだ名
push / pull
GitHubへ送る / GitHubから取ってくる
clone
GitHubのリポジトリを手元に丸ごと複製すること
.gitignore
記録しないファイルを書いておく設定。node_modules などを除外する
stash
作業中の変更を一時的に棚上げする機能。戻すときに競合が起きることがある

最後に Gitは壊すのが難しいようにできています。一度コミットしたものは、 たとえ消したように見えても履歴の中に残っていることがほとんどです。 怖がらずに git status と git log で 今どうなっているかを確かめながら進めてください。
