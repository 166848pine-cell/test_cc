1このアプリは何をしているのか

まず全体像から。実は「自分のサーバー」を1台も持っていません。

PinRoute はあなたのブラウザの中だけで動くアプリです。 地図の絵や住所の情報だけを、外部の無料サービスから借りてきています。

図1 — 動いている場所と、借りているもの

あなたのブラウザ 計算・表示・保存はすべてここ
⇄
地理院タイル 地図の絵
国土地理院 住所 → 緯度経度
Nominatim 施設名 → 緯度経度

この図に「PinRouteのサーバー」は出てきません。だから維持費が0円です。

たとえば「東京駅」と入力したとき、ブラウザは国土地理院に 「東京駅の場所を教えて」と聞き、返ってきた緯度経度をもとに、 地図の絵の上にピンを描いています。この一連の作業をしているのは、 あなたのパソコンの中のブラウザです。

2ふつうのWebサービスとの違い

「サーバーがある/ない」の違いが、費用と公開のしやすさを決めています。

よくあるWebサービス(動的サイト)

  • 会員登録やデータ保存のためにサーバーが常に動いている
  • アクセスのたびにサーバーがページを組み立てる
  • サーバー代・データベース代が毎月かかる
  • 止まると誰も使えない

PinRoute(静的サイト)

  • 置いてあるのはただのファイル(HTML・JavaScript・CSS)
  • アクセスされたらファイルをそのまま渡すだけ
  • ファイルを置く場所は無料のところがたくさんある
  • 組み立てる処理がないので、壊れにくく速い

ここが要点 「静的サイト」とはファイルを配るだけのWebサイトのことです。 料理にたとえると、注文を受けてから調理する店(動的)ではなく、 出来上がった弁当を棚に並べて持って行ってもらう店(静的)です。 棚を貸してくれるサービスは無料のものが多く、これがGitHubで公開できる理由につながります。

3フォルダの中身

「人が書くもの」と「機械が作るもの」の2種類があります。

pinroute/アプリ本体のフォルダ
├── index.html書く 画面の骨組み。ボタンや入力欄の置き場所
├── src/書く プログラム本体(17ファイル・約5,100行)
│   ├── main.ts起動して、部品どうしをつなぐ
│   ├── geocode.ts住所を外部サービスに問い合わせる
│   ├── rank.ts検索結果を「それらしい順」に並べ替える
│   ├── mapview.ts地図とピンを描く
│   ├── callout.ts引き出し線つきの情報ブロックを描く
│   ├── ui.ts左側パネルの表示と操作
│   └── style.css見た目(色・大きさ・並べ方)
├── tests/書く 動作を自動で確かめるプログラム(約2,500行)
├── docs/書く 説明書・サンプルCSV・このページ
├── package.json書く 使う道具の一覧と、作業の名前(build / test など)
├── node_modules/自動取得 道具の実体。約119MB・129フォルダ。公開しない
└── dist/自動生成 これが公開するもの
    ├── index.html10KB
    ├── assets/JavaScript 250KB + CSS 35KB
    └── PinRoute.html全部を1つに詰めた版(297KB)。ダブルクリックで開ける
書く 人が編集する。
これが「元」
自動取得 ネットから落としてくる道具。
消してもまた入れられる
自動生成 元から機械が作る。
消しても作り直せる

なぜ node_modules と dist を公開しないのか どちらも元のファイルから作り直せるからです。119MBもあるものを毎回持ち運ぶ必要はなく、 「元」と「作り方」さえあれば、必要なときに同じものができます。 この考え方が、次の「ビルド」と「GitHubでの公開」の土台になります。

4「ビルド」とは何か

人が読みやすい形 → ブラウザが読める形に翻訳・整理する作業です。

src/ の中身は、そのままではブラウザが読めません。理由は3つあります。

図2 — ビルドで起きていること

src/ の17ファイル + index.html TypeScript という書きやすい言語で書かれている。ファイルが多い
↓  npm run build
ビルドの中でやっていること ① 翻訳:TypeScript → ブラウザが読めるJavaScript
② まとめる:17個 + 部品(Leaflet)を1つのファイルに
③ 縮める:改行や空白、人間用の名前を削って小さくする
↓
dist/ HTML 1つ + JavaScript 1つ + CSS 1つ。これならブラウザがそのまま読める

npm run build と打つだけでこれが全部行われます。 「npm」は道具を管理するしくみ、「run build」は package.json に書いてある作業の名前です。

打つコマンド やること
npm install 使う道具(node_modules)をネットから揃える。最初の1回だけ
npm run dev 編集しながら試すための簡易サーバーを立てる
npm run test 動作が壊れていないか自動で確かめる(98項目)
npm run build 公開できる形(dist/)を作る

5ファイルを直接開くと動かない理由

これはPinRouteの不具合ではなく、ブラウザの安全上のルールです。

dist/index.html をダブルクリックしても、画面は出るのに地図が表示されません。 原因はアドレスの種類にあります。

file:// で開いたとき

file:///C:/.../dist/index.html

  • ブラウザは「どこの誰のファイルか分からない」と判断する
  • 安全のため、別ファイルのJavaScriptやCSSの読み込みを禁止する
  • 結果:文字だけ出て、地図も検索も動かない

http:// で開いたとき

https://～.github.io/～/

  • 「このサイトのファイル」という所属がはっきりする
  • 同じサイトの中のファイルは自由に読み込める
  • 結果:すべて正常に動く

図3 — だから「1ファイル版」を用意している

dist/index.html(3ファイル構成)

index.html
↓ 読みに行く
assets/～.js
assets/～.css

file:// ではこの矢印が禁止される

dist/PinRoute.html(1ファイル)

PinRoute.html
HTML + JavaScript + CSS
すべて中に入っている

読みに行く必要がないのでどこでも動く

6なぜGitHubで公開できるのか

GitHub Pages は「ファイルを配るだけの棚」を無料で貸してくれるからです。

GitHub はもともとプログラムの保管庫です。 そこに「GitHub Pages」という機能があり、 指定したフォルダの中身を、そのままWebサイトとして配ってくれます。

図4 — 公開されるまでの道すじ

あなたのPC src/ を編集
→
GitHub 保管庫
(元のファイル)
→
GitHub Actions 代わりにビルド
→ dist/ を作る
→
GitHub Pages dist/ を配る棚
→
世界中の
ブラウザ URLを開くだけ

なぜ無料で成り立つのか

Pages がすることはファイルを渡すだけだからです。 計算もデータベースも必要ありません。 しかもPinRouteは全部あわせて300KB程度(写真1枚ぶんくらい)しかないので、 配る側の負担がとても小さいのです。

住所検索や地図はどこから来るのか GitHubからではありません。閲覧者のブラウザが、国土地理院などに直接聞きに行きます(図1)。 つまり利用者が増えても、GitHub側の負担はほとんど変わりません。 そのかわり、外部サービスへの問い合わせは増えます。次の注意はそのためのものです。

公開版にルート機能が無い理由 ルート(道順)の計算に使っていた OSRM というサービスは、提供元が 「非商用かつ合理的な用途に限る」と定めており、 不特定多数に公開するアプリからの利用を認めていません。

そこで公開版ではルート計算を外し、代わりに 「Googleマップで開く」ボタンを残しています。 これは普通のリンク(URLを開くだけ)なので、利用制限がありません。 手元で使う PinRoute.html にはルート機能が入っています。

7公開までの流れ

1回設定すれば、あとは「保存して送る」だけで自動更新されます。

図5 — GitHub Actions が自動でやること

① あなたが GitHub に送る(push) 送るのは src/ などの「元」だけ。dist/ も node_modules/ も送らない
↓ 自動で始まる
② 作業用のパソコンを1台借りる GitHubが用意する。使い捨て
↓
③ 道具を揃える(npm ci) node_modules を作る
↓
④ 検査する(npm run lint / npm run test) 98項目の自動テスト。1つでも失敗したらここで止まり、公開されない
↓
⑤ ビルドする(npm run build) dist/ ができる
↓
⑥ dist/ を Pages に配置して公開完了 URLはいつも同じ。中身だけ新しくなる

この手順は .github/workflows/deploy-pinroute.yml というファイルに書いてあります。 人がやると忘れがちな「テストしてから公開する」を、機械に必ずやらせるための仕組みです。

最初の1回だけ必要な設定 GitHubのリポジトリ画面で Settings → Pages → Source を 「GitHub Actions」に切り替えてください。これで棚が有効になります。

8住所を探すしくみ

2つのサービスを使い分けて、無駄な問い合わせをしない工夫をしています。

図6 — 「六本木ヒルズ」と入力してから、ピンが立つまで

入力された言葉
↓
① 前に調べたことがあるか確認 あればそれを使う(外部には聞かない)
↓ 初めての言葉なら
② 国土地理院に聞く 日本の住所に強い。「東京都新宿区西新宿2-8-1」などはここで解決
↓ 十分な答えが出なければ
③ Nominatim にも聞く 施設名に強い。「六本木ヒルズ」のような建物名はここで解決
↓
④ それらしい順に並べ替えて、重複をまとめる この処理が無いと、まったく関係のない地点が候補の先頭に来てしまう
↓
⑤ 候補を表示 / 1件に決まればそのままピン

①の「前に調べたか確認」は必須の仕組みです。 Nominatim の利用規約に「結果は必ず保存し、同じ問い合わせを繰り返さないこと」と明記されているためです。 同じ言葉を2回目に検索したときは、外部への問い合わせが0件になります。

③をいつ呼ぶかも調整しています。 「東京駅」のようにぴったり一致したときや、住所らしい入力のときは、 国土地理院の答えで十分なので Nominatim には聞きません。公開サービスへの負担を減らすためです。

9データはどこにあるのか

サーバーが無いので、保存先はあなたのブラウザと、URLの中だけです。

図7 — 登録したピンの居場所

ふだんの保存

ピンの情報
↓ 自動保存
ブラウザの中の保管場所
(localStorage)

タブを閉じても残ります。ただし別のパソコンや別のブラウザからは見えません。 閲覧履歴を消すと一緒に消えます。

人に渡すとき(共有URL)

ピンの情報
↓ 文字に変換
https://…/#s=eyJ2IjoxLCJwIjpb…

URLそのものにピンの中身が入っています。 どこかに預けているわけではないので、リンクを知っている人だけが見られます。

つまり 運営者がピンの内容を見ることはできません。会員登録も不要です。 そのかわりバックアップも自動では取られません。 大事な組み合わせは共有URLを控えておくのが安全です。

10用語辞典

このページと開発まわりでよく出てくる言葉です。

静的サイト
ファイルを配るだけのWebサイト。サーバーで計算しないので安く速い
ビルド
人が書いた元のファイルを、ブラウザが読める形にまとめ直す作業
TypeScript
JavaScriptに「型」の仕組みを足した言語。書き間違いを事前に見つけやすい
npm
部品や道具を集めてくる仕組み。npm install で揃える
node_modules
集めてきた道具の置き場。作り直せるので公開も保管もしない
dist
distribution(配布)の略。公開する完成品が入る
リポジトリ
GitHub上のプロジェクトの保管庫。変更の履歴も残る
push
手元の変更をGitHubに送ること
GitHub Actions
pushをきっかけに、検査やビルドを自動で実行してくれる仕組み
GitHub Pages
指定したフォルダをWebサイトとして無料で配ってくれる機能
API
他のサービスに機械的に問い合わせるための窓口
ジオコーディング
住所や施設名から緯度経度を求めること
キャッシュ
一度得た結果を取っておいて、次は聞き直さずに使うこと
localStorage
ブラウザがサイトごとに用意する保存場所。閉じても残る
CORS
「どのサイトのファイルなら読み込んでよいか」を決めるブラウザの安全ルール
