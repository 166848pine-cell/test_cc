# 設計ドキュメントとの差分・改善提案

## A. 設計ドキュメントから意図的に変更した点

実機で動かしたところ仕様どおりでは実用にならなかった箇所を変更した。
いずれも要件定義書(01)の目的には沿っているが、基本設計(02)・詳細設計(03)・
テスト計画(04)の記述とは異なるため、ここに残す。

### A-1. 検索候補の並べ替えと重複統合を追加(最重要)

**変更前の問題**: 基本設計 §5.1 は国土地理院APIの結果をそのまま候補にする前提だが、
このAPIは関連度順に並んでいない。「東京駅」で53件返り、先頭5件は

```
北海道札幌市東区 / 北海道東神楽町東 / 北海道佐呂間町東 / 北海道湧別町東 / 北海道長沼町東
```

となる(本命の「東京駅」は配列末尾)。**受け入れ基準1「『東京駅』の入力でピンが立つ」を満たせない。**

**変更内容**: `src/rank.ts` を追加し、取得後に一致度で並べ替え・重複統合・足切りを行う。
詳細は README「検索の仕組み」を参照。

### A-2. 国土地理院とNominatimを「0件時のみ切り替え」から「常に統合」へ

**変更前の問題**: FR-01・基本設計 §5.1 は「国土地理院が0件ならNominatim」だが、
国土地理院は施設名に弱く、**0件ではなく間違った結果を返す**ケースがある。
「札幌市時計台」→「北海道札幌市」(市の代表点)が返るため、フォールバックが発動せず
受け入れ基準の想定地点にピンが立たない。「六本木ヒルズ」も郵便局しかヒットしない。

**変更内容**: 国土地理院 → Nominatim の順に問い合わせるところは変えず、
結果を捨てずに統合して並べ替える。国土地理院で候補が得られている場合、
Nominatimは「間に合えば使う補完」として扱い、NFR-07(3秒以内)の残り時間だけ待つ。

**テスト計画への影響**: IT-01「GSIヒット時はNominatimを呼ばない」は成立しなくなるため、
「GSIがヒットしてもNominatimで補完し、両者を統合して返す」に変更した。
あわせて IT-01b(Nominatim障害時のグレースフルデグラデーション)と
IT-01c(両系統失敗時のE2)を追加している。

Nominatimへのリクエストは1検索につき最大1回で、1req/秒の制限(NFR-04)は維持している。

### A-3. マーカーを円形からしずく型へ

基本設計 §2.3 は「円形divIcon、直径28px」だが、円を座標に重ねると
どの地点を指しているかが曖昧になる。地図上で指し示す点が明確になるよう、
先端が座標を指すしずく型(30×36px、番号入り、白縁)に変更した。色・番号は仕様どおり。

### A-4. `crypto.randomUUID` に代替経路を用意

詳細設計 §4.1 は `crypto.randomUUID()` 固定だが、これはセキュアコンテキスト
(https/localhost)でしか使えない。LAN内のhttp配信などで例外になりアプリが起動しないため、
利用できない環境では乱数IDにフォールバックする(`src/types.ts` の `newId`)。

### A-5. 共有URLのpayloadを畳んだ形式に変更

要件§5は「2,000文字を超える場合は発行時に警告する」と定めているが、
当初の実装は `AppState` をそのままJSON化していたため、
20件のピンで約2,900文字となり**ほぼ常に警告が出る**状態だった。
共有はFR-10の中心機能なので、payloadを次のように畳んだ。

- 復元時に再発行される `id` を含めない
- ピンを `[名称, 検索語, 緯度, 経度, 所在地]` の配列にしてキー名を省く
- 検索語が名称と同じなら空文字にし、復元時に埋め戻す
- 座標は小数6桁(約0.1m)に丸める

これで現実的な20件は2,000文字未満に収まる(UT-H07)。
日本語はUTF-8で1文字3バイト、さらにbase64で1.33倍になるため、
極端に長い名称ばかりの20件では依然2,000文字を超えるが、その場合は仕様どおり警告を出す。
旧形式のpayloadも引き続き復元できる(UT-H06)。

### A-6. ダブルクリックで開ける1ファイル版を追加

**変更前の問題**: `index.html` や `dist/index.html` をファイルとして直接開いても動かない。
ブラウザは `file://` のページから別ファイルのスクリプト・CSSを読み込むことをCORSで禁止しているため、
画面は表示されるが地図が出ず、検索も反応しない。要件は静的配信(GitHub Pages)を前提としているが、
手元で試すときの入口としては分かりにくい。

**変更内容**: `npm run build` で通常版に加えて `dist/PinRoute.html` を出力するようにした。
JSとCSSを1枚のHTMLに畳んであり、サーバーなしでそのまま開ける。
通常版(`dist/index.html` + `assets/`)は従来どおりのモジュール構成のままで、GitHub Pages 用の成果物は変わらない。

`vite.config.ts` に `--mode standalone` のビルドを追加し、`@types/node` を開発依存に加えた。

### A-7. E2Eのモバイル実行環境

テスト計画 §4 は「chromium + mobile viewport」だが、実装は `devices['iPhone 12']`
(WebKit)を指定していた。テスト計画どおり chromium + 375×667 に修正した。

## B. 定義済み機能の使い勝手として追加した表示・操作

新しい機能ではなく、既存機能(FR-03〜FR-07)を実際に使えるようにするための
表示と操作を追加した。「最高のユーザビリティを目指す」という指示に基づく。

| 追加 | 目的 |
|---|---|
| 候補・ピン一覧への所在地表示(例:「富士山《静岡県駿東郡小山町》」) | 同名候補の区別。国土地理院の市区町村コードから変換 |
| ピン間の区間距離・所要時間 | FR-07の総距離だけでは、どの区間が長いか分からない |
| 候補の ↑↓ + Enter 操作 | キーボードだけで検索から確定まで完結させる |
| 一覧の番号クリックで地図を該当地点へ | 一覧と地図の対応付け |
| 一覧ホバーでマーカー強調 | 同上 |
| 空状態の案内 | 初回訪問時に何をすればよいか分かるように |
| ピン件数表示(3 / 20 件) | 上限に達する前に気づけるように |
| 名称編集中は地図の表示範囲を動かさない | 編集のたびにfitBoundsが走ると操作しづらい |
| ルート計算中の表示 | 無反応に見えないように |
| ドラッグ用グリップ | 行のどこを掴めばよいか分かるように(名称入力欄と競合させない) |
| ダークモード対応 | OSのテーマに追従 |
| 地図コンテナのリサイズ追従 | 画面回転・分割比変更で地図が欠けるのを防ぐ |
| ルート応答の反映は区間行だけ差し替え | 遅れて返る応答でドラッグ操作や名称編集が中断されないように |

## B-2. 要件定義書の範囲を超えて追加した機能(利用者の依頼による)

01_requirements.md v1 には無い機能を、利用者の明示的な依頼で追加した。
「ドキュメントに定義のない機能の追加実装」を禁じる指示(00_claude_code_instructions.md)より
利用者の直接の依頼を優先している。要件定義書を更新する場合はこの節を反映すること。

| 追加機能 | 内容 |
|---|---|
| まとめて入力(`src/bulk.ts`) | 物件名・住所・駅徒歩などの列を含む表(タブ区切り/CSV)を貼り付けて一括登録する。列の役割は見出しと値から自動推定し、取り込み前にプレビューできる。失敗行は理由つきで残す |
| 情報ブロック(`src/callout.ts`) | 地図のプロットから引き出し線を伸ばし、その先のブロックに表の内容を表示する。不動産の査定資料で競合物件を並べる用途を想定 |
| ブロックの自由配置 | 見出しをドラッグして任意の位置へ。位置はピンからのピクセル差として保存し、地図を動かしても関係が崩れない |
| 表示項目の設定 | ブロックに出す項目と順番を変更、個別・全体の表示切り替え、配置の初期化 |
| ブロックの自動配置 | 初期位置を自動で決める。余裕があればピンの横、置ききれないときは地図の左右の端に振り分けて縦に並べる。地図が止まるたびに計算し直す(ドラッグしたものは対象外) |
| サンプルCSV | `docs/sample-properties.csv`。神保町駅から半径500m以内の実在の街区10件に、説明用の架空の物件名・賃料・面積を組み合わせたもの |
| ルート表示の切り替え | 物件の比較資料として使うときはルート線が邪魔になるため、表示のON/OFFを選べるようにした。OFFの間はOSRMへの問い合わせも行わない |
| 色・大きさの設定(`src/appearance.ts`) | ピン・情報ブロック・引き出し線・ルート線の色と大きさを、全体まとめてと地点ごとの2段構えで変えられる。6色 × 3サイズ |
| 項目のまとめて切り替え | 情報ブロックに出す項目を「すべて表示」「すべて隠す」で一括操作 |
| Googleマップリンクの独立 | ルート概要の中に置いていたため、ルート表示を消すとリンクも消えていた。ルート表示とは切り離し、2件以上あれば常に使えるようにした |
| 住所入力の強化 | 郵便番号・建物名・部屋番号が付いた住所でも、順に切り詰めて調べ直す |

データ構造は後方互換を保っている(`Pin.fields` / `Pin.labelOffset` / `Pin.labelHidden`、
`AppState.fieldOrder` / `hiddenFields` / `labelsVisible` はいずれも任意項目で、スキーマ版は `v: 1` のまま)。
共有URLにも情報ブロックの内容・配置・項目設定を載せているため、URLは以前より長くなる。

### A-8. 一般公開に向けた外部サービスの見直し

不特定多数への公開にあたり、各サービスの利用規約を確認して構成を変えた。

| サービス | 規約の内容 | 対応 |
|---|---|---|
| OSRM デモサーバー | 「非商用かつ合理的な用途に限る」。公開アプリからの利用を認めていない | 公開ビルドから外し、経路は「Googleマップで開く」で代替。手元用の1ファイル版だけが持つ |
| Nominatim | アプリ全体で1req/秒。**結果のキャッシュ必須**。利用者数が中程度であること | `src/geocache.ts` を追加(30日・最大300件)。国土地理院で答えが出ないときだけ呼ぶ |
| OSMタイル | 数値基準はないが「重い利用は予告なくブロック」 | 地理院タイル(淡色地図)に変更。出典の記載のみで利用でき、レート制限の定めもない |
| 国土地理院 | 出典の記載 | フッターと地図上に表示(従来どおり) |

要件定義書 NFR-01 は使用APIを「国土地理院 / Nominatim / OSRMデモサーバー / OSMタイル」と定めているが、
NFR-02(静的配信)・NFR-03(ランニングコスト0円)と一般公開を両立させるにはこの構成変更が必要だった。
ルート計算は要件 FR-07 の中心機能なので、手元用ビルドには残している。

## C. 実装していない提案(v2以降の候補)

要件定義書 §2.2 の対象外、またはドキュメントに定義がないため実装していない。

1. **巡回順の自動最適化(TSP)** — 20件までなら近似解を数十msで出せる。「最短順に並べ替え」ボタンが自然
2. **地図クリックでピン追加** — v2候補として要件に明記あり
3. **公開版でもルートを出す** — 自前のOSRMを立てる(サーバー費用が発生)、または OpenRouteService / GraphHopper の無料枠(APIキーが必要。静的サイトでは鍵が露出するため、ドメイン制限のある提供元を選ぶ必要がある)
3b. **徒歩・自転車ルート** — OSRMデモサーバーは `foot`/`bike` プロファイルを公開していないため、別の無料サービスが必要
4. **検索のインクリメンタル候補表示** — 入力中に候補を出す。Nominatimの1req/秒制限とレート配慮の兼ね合いを設計する必要がある
5. **国土地理院の結果を先に表示し、Nominatimの結果を後から差し込む** — 体感速度は上がるが候補の並びが動くため、良し悪しの検証が必要
6. **ピンのグループ分け・色分け** — 訪問日ごとに分けたい用途
7. **CSV/テキストの一括貼り付けで複数地点をまとめて登録** — 「複数地点をまとめて」という当初の目的に最も近い拡張
8. **ルートのGPX/KMLエクスポート**
8b. **資料としての書き出し(PDF・画像)** — 情報ブロック付きの地図をそのまま提出資料にしたい場合。印刷用CSSを足すのが手軽
8c. **情報ブロックの配置をさらに賢く** — 現状は「ピンの横」か「左右の端に縦積み」の2通り。引き出し線の交差を減らす配置や、ブロックの高さをそろえる整列があるとより資料らしくなる
8d. **ブロックの見た目の調整** — 文字サイズ・色・幅を利用者が選べるようにする
9. **共有URLのさらなる短縮** — A-5で畳んだ形式にしたが、日本語の名称が支配的でまだ長い。`CompressionStream('deflate-raw')` で圧縮すれば半分程度になる見込み(ただしデコードが非同期になるため起動処理の作り直しが必要)。座標を先頭ピンからの差分にする手もある
